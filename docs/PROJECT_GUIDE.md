# Project Guide — AI Driving Risk & Accident Severity Simulator

This document explains the whole project in plain language: what the data
is, what the model does, why every non-obvious decision was made, and how
each layer (ML → backend → Flutter → Flame) works. It's written for someone
who has limited ML/Flutter experience and needs to explain this project to
an instructor.

---

## 1. The big picture

```
Flutter + Flame (phone UI + 2D side-view driving scene)
        │  Speed slider + Seatbelt toggle (live controls);
        │  environment auto-changes every 10s
        ▼
FastAPI backend  (POST /predict)
        │  validates the request against the exact categories/ranges
        │  the model was trained on
        ▼
Saved scikit-learn Pipeline (preprocessing + RandomForestClassifier)
        │  predict_proba() → a real probability for each of 3 classes
        ▼
FastAPI returns { prediction, risk_label, probability, probability_percent, probabilities }
        ▼
Flutter shows SAFE 🟢 / MINOR RISK 🟡 / HIGH RISK 🔴 + the percentage
```

Every prediction shown in the app is the real output of
`pipeline.predict_proba()` running on the FastAPI server. Nothing is
hardcoded (there is no `if speed_kmh > 100: return "HIGH RISK"` anywhere in
this codebase).

## 2. How this dataset was chosen (project history)

Two other datasets were investigated and rejected before settling on
BDRoadRisk. This history matters — it's exactly the kind of thing an
instructor will ask about.

**Attempt 1 — the originally-provided dataset.** Before writing any training
code, real cross-validated models (Logistic Regression, Random Forest) were
run against it. ROC-AUC came back at 0.50–0.53 — statistically
indistinguishable from a coin flip. Every feature's correlation with the
target was ~0.00–0.04. This dataset is a synthetic/randomly-generated
Kaggle dataset with no genuine relationship between any feature and the
target at all. It was rejected outright.

**Attempt 2 — a real police-recorded dataset (Addis Ababa, Ethiopia).**
12,316 real accident records with genuine, cross-validated signal (ROC-AUC
~0.58–0.65). This was a legitimate dataset, but it had no real vehicle-speed
column and no seatbelt column, so the original "Speed slider + Seatbelt
toggle" concept had to be replaced with unrelated substitutes (driving
experience, vehicle type) to make an honest model. That compromised the
core game concept this project was supposed to demonstrate.

**Final choice — BDRoadRisk.** A large, structurally rich synthetic
benchmark that genuinely contains `speed_kmh` (real vehicle speed, distinct
from the posted speed limit) and `seatbelt_worn` — restoring the original
concept with real, matching columns. The tradeoff, disclosed prominently
throughout this project, is that BDRoadRisk is **100% synthetic** rather
than real-world data. See §3.

## 3. The dataset — BDRoadRisk

**BDRoadRisk: Large-Scale GPS Traffic Accident Severity Dataset.** Mendeley
Data, DOI `10.17632/m33bsbsgx2.3`, CC BY 4.0. Published by Dewanjee &
Muntaha, Chittagong University of Engineering & Technology.

- **10,000,000 rows**, 23 features + 1 target, simulating GPS-based traffic
  events on the road networks of Dhaka and Chittagong, Bangladesh.
- **100% synthetic.** This is stated directly in the dataset's own
  description: *"10 million synthetic GPS-based traffic event records...
  Severity labels are generated using a context-driven probabilistic
  model... A 1.8% boundary label noise is applied at the No_Accident/Minor
  boundary to reflect real-world reporting ambiguity."* No real accidents,
  no real police logs, no real telematics — every row was generated by a
  simulation.
- **Target:** `accident_severity` — three classes: `No_Accident` (74.4%),
  `Minor` (17.3%), `Major` (8.3%).

### Sampling strategy

Loading all 10,000,000 rows for iterative development is unnecessary and
slow. This project trains on a fixed, reproducible **500,000-row systematic
sample**: every 20th row of the original CSV (row index % 20 == 0), taken in
a single streaming pass over the full file. This is deterministic — no
random seed involved, so it reproduces identically from the same source
file — and its class balance was verified to closely match the full
dataset:

| | No_Accident | Minor | Major |
|---|---|---|---|
| Full 10M dataset | 74.41% | 17.30% | 8.28% |
| 500k sample | 74.35% | 17.34% | 8.31% |

### What "risk %" means here

Because the dataset only contains generated event records (there's no
concept of "a real trip where nothing happened, logged in the real world"),
the model answers: *"given these conditions, how likely is this event to
be classified Minor or Major rather than No_Accident?"* — a real,
model-computed probability, but computed against a synthetic benchmark, not
real-world accident statistics. **This is the single most important
disclosure in the whole project: the output probability must not be
interpreted as a real-world accident probability.**

## 4. Feature selection and leakage analysis

BDRoadRisk ships 23 features. Its own `Data_Dictionary.txt` (included in
`ml/dataset_bdroadrisk/`) splits them into 14 "Pre-Accident" features
(environmental/vehicle/driver conditions that exist before any event) and 9
"Post-Accident" features (behavioral/incident factors). Reading that
dictionary's own text revealed that some of those "Post-Accident" features
were generated with their **distributions directly conditioned on the
target label** — meaning a model using them wouldn't be discovering a real
relationship, it would be partly decoding the label out of a feature that
was built *from* that label.

### Excluded features

| Feature | Why excluded |
|---|---|
| `junction_type` | The dictionary states it was *"Generated using a 50/50 blend of road-class-driven **and severity-driven** distributions."* Half its value is sampled from the answer. Confirmed leakage. |
| `visibility_km` | The dictionary states it is *"Driven by weather condition **and severity class**."* Same problem — and it was the single highest-importance feature (~20%) in an unrestricted model, which is a red flag, not a discovery. |
| `acceleration_ms2` | Describes braking at the specific instant of an event ("hard braking is a strong signal for Major"), not a pre-existing condition. There's no meaningful "current acceleration" the way there's a "current speed" — it only makes sense in hindsight of a specific incident, so it doesn't fit a real-time simulator regardless of the leakage question. |
| `reaction_time_sec` | Same reasoning — only meaningful in hindsight of a specific event, not something a driver "has" as an ongoing state. |
| `temperature_celsius` | The dictionary explicitly labels it *"non-predictive... Intentional noise feature."* No signal by design; including it would only add noise. |

Also excluded, but for demographic-neutrality rather than leakage: nothing
in this version — unlike the earlier RTA-based version of this project,
`driver_age` and `driver_experience_level` are kept here as **fixed
context** (see below), not exposed as demographic sliders.

### The 18 features actually used

```python
LIVE_CONTROLS   = ["speed_kmh", "seatbelt_worn"]
AUTO_ENVIRONMENT = ["weather_condition", "road_surface", "light_condition", "time_of_day"]
FIXED_CONTEXT   = ["road_class", "road_quality", "speed_limit_zone", "vehicle_type",
                    "vehicle_age_years", "driver_age", "driver_experience_level",
                    "alcohol_influence", "month", "latitude", "longitude", "traffic_density"]
```

- **Live controls (2):** the two things the player actually drags/taps in
  Flutter — `speed_kmh` (0–200 km/h, the dataset's own documented range)
  and `seatbelt_worn` (Yes/No). These are the original project concept,
  restored with real matching dataset columns.
- **Auto-changing environment (4):** cycled automatically every 10 seconds
  by 5 predefined scenarios (see §8 below) — `weather_condition`,
  `road_surface`, `light_condition`, `time_of_day`.
- **Fixed context (12):** required by the model, but not exposed as UI
  controls, to keep the game simple. Each is fixed to the statistical
  mode (categorical) or median (numeric) of the training sample — "a
  typical driver in a typical vehicle on a typical road" — except
  `vehicle_type`, fixed to `"Car"` to match the single car sprite. Exact
  values live in `ml/model/fixed_context.json`:

  | Feature | Fixed value |
  |---|---|
  | `road_class` | `primary` |
  | `road_quality` | `Good` |
  | `speed_limit_zone` | `80` |
  | `vehicle_type` | `Car` |
  | `vehicle_age_years` | `3` |
  | `driver_age` | `35` |
  | `driver_experience_level` | `Experienced` |
  | `alcohol_influence` | `None` |
  | `month` | `6` |
  | `latitude` / `longitude` | Dhaka city centre |
  | `traffic_density` | `55` |

**Important consequence, stated plainly:** some of these fixed-context
features (`driver_experience_level`, `alcohol_influence`) carry real
predictive weight in the model but never vary at inference time in this
simulator. The live predictions you see while playing only explore the
slice of the model's input space where the driver is experienced, sober,
and driving a typical car — not the full range the model actually learned
from.

## 5. Preprocessing, model selection, and evaluation

### Pipeline

```
categorical features → SimpleImputer(fill_value="Unknown") → OneHotEncoder(handle_unknown="ignore")
numeric features      → SimpleImputer(strategy="median")    → StandardScaler()
                                    ↓
                          RandomForestClassifier
```

The entire pipeline (imputers + encoder + scaler + classifier) is saved as
**one** joblib file (`ml/model/risk_pipeline.joblib`). The FastAPI server
loads that one file and calls `.predict_proba()` directly on a raw
DataFrame — it never has to know about one-hot encoding or missing-value
handling itself.

### Train/test split and cross-validation

An 80/20 **stratified** train/test split (`train_test_split(..., stratify=y,
random_state=42)`) keeps the 74/17/8 class balance in both halves. Model
comparison uses **5-fold stratified cross-validation** on the training
split only — the test set is never touched until final evaluation. Cross-
validation means: split the training data into 5 equal folds, train on 4 of
them and validate on the 5th, repeat 5 times so every fold is used for
validation once, then average the scores. This gives a much more reliable
estimate of how a model generalizes than a single train/test split would,
because it isn't dependent on which particular rows happened to land in the
test set.

### Models compared

| Model | CV Accuracy | CV F1 (macro) | CV Precision (macro) | CV Recall (macro) | CV ROC-AUC (OvR macro) |
|---|---|---|---|---|---|
| Logistic Regression | 0.802 | 0.725 | 0.697 | 0.773 | 0.917 |
| **Random Forest (chosen)** | **0.811** | **0.731** | **0.705** | **0.772** | **0.921** |
| Extra Trees | 0.783 | 0.690 | 0.662 | 0.735 | 0.897 |

**RandomForestClassifier was selected** — the highest cross-validated
ROC-AUC of the three, and consistently competitive (not just highest) on
every other metric too.

### Why ROC-AUC and macro-averaged metrics, not raw accuracy

`accident_severity` is imbalanced: 74.4% No_Accident, 17.3% Minor, 8.3%
Major. A model that always predicts "No_Accident" would score ~74%
accuracy while being completely useless — it would never once flag a
dangerous situation. ROC-AUC (one-vs-rest, macro-averaged across all 3
classes) measures how well the model ranks each class above the others,
regardless of how imbalanced they are. Precision, recall, and F1 are
reported as **macro** averages (the unweighted mean across the 3 classes)
rather than weighted, specifically so the rare-but-important `Major` class
counts as much as the common `No_Accident` class in the headline number —
a weighted average would let strong performance on the majority class hide
weak performance on the class that matters most for a safety tool.

### Final held-out test set results (100,000 rows, untouched until this point)

```
accuracy:            0.811
precision (macro):   0.704
recall (macro):      0.770
f1 (macro):           0.730
roc_auc (OvR macro): 0.920
```

Confusion matrix (rows/columns ordered `[Major, Minor, No_Accident]`):

```
              Predicted:
              Major   Minor   No_Accident
Actual Major   6749    1502          64
Actual Minor   2699   11263        3378
Actual No_Acc   380   10913       63052
```

**What this means in plain language:** on the `Major` class specifically —
the one that matters most — the model catches 6,749 of 8,315 actual Major
cases (recall ≈ 81%), at the cost of some false alarms (precision ≈ 69% for
that class, per `classification_report`). This is a real, decent, honestly-
reported result on a benchmark with genuine (if synthetic) structure. It is
not the near-perfect ~0.98 AUC that including the leakage-tainted features
(`junction_type`, `visibility_km`) would have produced — that gap between
"if we'd used everything" and "what we actually report" is itself evidence
this project took the leakage analysis seriously rather than chasing the
highest possible number.

### What `predict_proba()` and "risk %" mean

`pipeline.predict_proba(X)` returns a probability for *each* of the 3
classes (they sum to 1.0). The API returns all three (`probabilities` in
the response) plus the single highest one as the headline
`probability`/`probability_percent`. Nothing is post-processed except
rounding for display — no manual boosting, no fabricated confidence.

## 6. Backend (FastAPI) — for beginners

- **FastAPI** is a Python web framework for building APIs. You write normal
  Python functions with type hints, and FastAPI turns them into HTTP
  endpoints with automatic request validation.
- **Project layout:**
  - `backend/main.py` — the FastAPI app, route definitions (`/health`,
    `/categories`, `/predict`), and startup logic that loads the model once.
  - `backend/schemas.py` — Pydantic models (`PredictRequest`,
    `PredictResponse`) defining exactly what a request/response looks like.
  - `backend/services/predictor.py` — the `Predictor` class: loads the
    saved pipeline + category/range/fixed-context JSON files once at
    startup, validates incoming requests, merges the 6 live fields with the
    12 fixed-context defaults into one row, and calls `predict_proba()`.
- **`POST /predict`** is the one endpoint that matters. Request (JSON —
  JavaScript Object Notation, a plain-text way to represent structured
  data): `speed_kmh`, `seatbelt_worn`, `weather_condition`, `road_surface`,
  `light_condition`, `time_of_day`. Response: `prediction`, `risk_label`
  (SAFE/MINOR RISK/HIGH RISK), `probability`, `probability_percent`, and
  `probabilities` (all 3 classes, for transparency).
- **Pydantic** validates types and simple constraints automatically (e.g.
  `seatbelt_worn` is a `Literal["Yes","No"]`, so anything else is rejected
  with a 422 before your code even runs; `speed_kmh` has `ge=0, le=250`).
  `Predictor._validate()` does the rest: checking free-text category
  fields (`weather_condition`, etc.) against the exact vocabulary the
  model saw during training (`ml/model/categories.json`), and numeric
  fields against the training data's observed range
  (`ml/model/numeric_ranges.json`).
- At startup (`predictor.load()`, called via FastAPI's `lifespan` context
  manager), the saved pipeline is loaded once into memory — it does **not**
  reload on every request, which keeps predictions fast.
- Preprocessing happens automatically: because the saved pipeline
  *includes* the imputers, encoder, and scaler, calling
  `pipeline.predict_proba(raw_dataframe)` does all of that internally. The
  API code never manually encodes anything.
- Errors are handled explicitly and the server never crashes on a bad
  request: unrecognized category → 422 with the exact valid list; number
  out of range → 422; missing field → 422 from Pydantic; any unexpected
  failure during prediction → 500, logged.

## 7. Flutter — for beginners

- The **UI** is plain Flutter widgets: `Column`, `Container`, `Slider`, a
  custom toggle — no custom framework. Dark theme matching the original
  mockup.
- **`lib/models/scenario.dart`** — the `Scenario` class and the 5
  predefined environment presets (`kScenarios`). `toApiFields()` builds the
  exact JSON body sent to the backend from a scenario plus the current
  speed/seatbelt state.
- **`lib/models/risk_result.dart`** — the `RiskResult` class, parsed
  entirely from the API's JSON response (`RiskResult.fromJson`). Nothing in
  this file invents a risk value; if the field isn't in the response, it
  isn't in the object.
- **`lib/api/risk_api_client.dart`** — `RiskApiClient` uses the `http`
  package to `POST` a JSON body to `http://127.0.0.1:8000/predict` and
  parses the JSON response back into a `RiskResult`. If the server can't be
  reached, the app shows an honest "backend unreachable" banner instead of
  fabricating a number.
- **`lib/ui/controls_panel.dart`** — the Speed `Slider` (0–200 km/h) and the
  Seatbelt toggle, the project's two live player controls.
- **`lib/ui/simulator_page.dart`** — the `SimulatorPage` state:
  - Environment changes automatically every 10 seconds
    (`Timer.periodic(const Duration(seconds: 10), ...)`), picking a new
    `Scenario` at random from `kScenarios` (never repeating the current one
    back-to-back).
  - **Throttling:** a prediction is requested immediately when the
    environment changes or the seatbelt is toggled (both discrete, instant
    choices), but the speed slider uses a **350ms debounce** — dragging it
    doesn't fire a request per pixel, only once the user pauses.
- **`lib/ui/risk_dashboard.dart`** — renders SAFE/MINOR RISK/HIGH RISK with
  the matching color and emoji, the percentage, a 20-segment meter bar, and
  the full 3-class probability breakdown — all read straight off the
  `RiskResult` the API returned.

## 8. Flame — for beginners

- **Flame** is a 2D game engine built on top of Flutter's canvas. It's used
  here purely to draw and animate the side-view driving scene — it is not a
  "game" in the sense of having rules, scoring, or win/lose states.
- **`lib/game/drive_game.dart`** — `DriveGame extends FlameGame`. Its
  `onLoad()` builds the scene once: a gradient sky, two hill silhouettes
  (drawn with `Path`, not sprites), a grass strip, a road, and a car — all
  simple flat shapes (`RectangleComponent`, custom `render()` methods).
- **The car never moves.** Only the lane markings scroll
  (`_lanes.scroll(...)` in `update(dt)`), at a speed tied to the player's
  current `speedKmh` — a purely visual cue (faster scenery = feels faster)
  that has no bearing on the actual API request, which sends the exact
  `speed_kmh` value directly regardless of how fast the lines happen to be
  scrolling on screen.
- **`applyScenario()`** swaps the sky/road colors and light/weather
  overlays whenever the environment changes — this mirrors the same
  `Scenario` object sent to the API, but the rendering logic has zero
  influence on the prediction; they're kept in sync by both reading the
  same source of truth, not by the visuals feeding back into the model.
- **Weather effects** (`_WeatherLayer`): rain lines, a fog overlay, a
  night tint + headlight beam, and — only during the Storm scenario —
  decorative wind-gust streaks. **Wind is explicitly NOT sent to the ML
  model** (BDRoadRisk has no wind feature); it's labeled "visual only" in
  the UI and only ever affects rendering.
- **No crash mechanic, no physics, no game-over state, no health bar** —
  by design. The purpose of the Flame scene is to visualize the same
  conditions being sent to the model, not to be a game in its own right.
